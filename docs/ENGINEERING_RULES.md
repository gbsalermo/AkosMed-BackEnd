# AkosMed Engineering Rules

This document is the compact technical guardrail for implementation and review.

---

# 1. Language and naming

The project uses English consistently for:

- packages;
- classes;
- fields;
- methods;
- enums;
- DTOs;
- database tables/columns when explicitly named;
- API paths;
- error codes;
- technical documentation.

Avoid mixing Portuguese and English in code.

Comments should be rare and should explain decisions or non-obvious constraints, not restate what a well-named method already says.

---

# 2. Architecture

Style:

```text
modular monolith by feature
```

Target package layout:

```text
br.com.akosmed
├── shared
├── tenant
├── identity
├── professional
├── patient
├── scheduling
├── clinical
├── care
├── diagnostics
├── prescription
├── document
├── storage
├── notification
└── audit
```

Inside a feature:

```text
controller
dto
├── request
└── response
entity
repository
service
```

Create packages/classes only when the feature is implemented. Do not populate the repository with empty scaffolding.

---

# 3. Request flow

```text
HTTP
↓
security filter
↓
authenticated tenant/user context
↓
controller
↓
request DTO + validation
↓
service
↓
repository
↓
JPA/Hibernate
↓
database
```

Responsibilities:

```text
Controller → HTTP contract only
Service    → business rules, authorization, orchestration, transaction
Repository → persistence/query
Entity     → persistent domain state and local invariants
DTO        → API input/output contract
```

Controllers never call repositories directly.

# 4. Git workflow

`main` is the stable branch.

Every functional or structural change uses a branch and Pull Request.

Flow:

```text
main
→ small branch
→ implementation
→ local validation
→ automated tests
→ Postman validation when applicable
→ documentation update
→ Pull Request
→ review
→ merge into main
```

Suggested branch names:

```text
docs/mvp-blueprint
feat/project-foundation
feat/tenant
feat/unit
feat/auth
feat/patient
feat/appointment
fix/appointment-conflict
```

Do not implement new backend functionality directly on `main`.

# 5. IDs

Canonical pattern:

```text
Long id       → internal PK/FK, joins and locks
UUID publicId → API/DTO/URL/JWT/integrations
```

Rules:

- every externally addressable persisted entity has a publicId;
- publicId is generated by the application;
- publicId is unique and immutable;
- create requests cannot choose publicId;
- responses never expose internal Long IDs;
- public URLs use UUIDs;
- request relationships use `...PublicId`;
- UUID does not replace authorization.

Internal numeric IDs are acceptable and preferred for JPA relationships in the MVP.

---

# 6. Multi-tenancy

Model:

```text
Shared Database
+ Shared Schema
+ tenant_id
```

Tenant is resolved from authenticated server context.

Never trust:

```text
tenantId from request body/query/header as an internal database identifier
```

Tenant-scoped repository boundaries prefer patterns such as:

```text
findByPublicIdAndTenantId(...)
findAllByTenantId(...)
existsBy...AndTenantId(...)
```

A UUID that exists in another tenant should normally behave as not found.

Unit selection is not tenant selection. A client may provide `unitPublicId` for an operation, but the backend must verify that:

```text
unit belongs to active tenant
+
current user may access that unit
```

---

# 7. DTOs

Use separate request and response DTOs from the beginning.

Examples:

```text
PatientCreateRequest
PatientUpdateRequest
PatientResponse
PatientSummaryResponse
```

Rules:

- request contains only writable fields;
- response contains only useful public fields;
- no Entity as HTTP body;
- no internal Long ID;
- no password hash;
- no storage key;
- no tenant internal ID;
- relationship references use UUID public IDs;
- avoid oversized DTOs;
- use summary responses for nested resources when appropriate.

---

# 8. Entities and JPA

Rules:

- no `@ManyToMany` for domain relationships;
- use explicit link entities;
- to-one relations should be LAZY when practical;
- do not switch to EAGER to hide session/query problems;
- avoid unnecessary bidirectional collections;
- do not use `CascadeType.ALL` by convenience;
- do not use destructive cascade/orphan removal on clinical history;
- enums persist as STRING;
- money uses BigDecimal;
- date/time types follow real semantics;
- entities are not serialized directly.

Do not use Lombok `@Data` blindly on JPA entities. If Lombok is introduced, use narrow annotations intentionally.

---

# 9. Database strategy

## Early development

Use H2 to evolve the domain quickly.

Recommended development/test behavior:

```text
dev  → H2 + Hibernate-managed schema
 test → in-memory H2 + isolated schema lifecycle
```

Avoid H2-specific SQL or behavior.

## PostgreSQL stabilization

After the domain is stable:

```text
PostgreSQL
+ Testcontainers
+ ddl-auto=validate
```

Schema migration tooling is not required during the early H2 stage.

Before production PostgreSQL, an explicit migration strategy is mandatory. Flyway remains the recommended default because it versions schema evolution, but the final tool choice is made before the PostgreSQL production stage rather than forced during initial development.

# 10. Secrets and configuration

Never commit real:

```text
DB_URL
DB_USER
DB_PASSWORD
JWT_SECRET
storage credentials
SMTP credentials
API keys
```

Use environment variables or a secret manager.

A safe `.env.example` may document required variable names without real values.

# 11. HTTP contract

Base path:

```text
/api/v1
```

Use actions for important state transitions rather than generic updates.

Examples:

```http
PATCH /appointments/{publicId}/confirm
PATCH /appointments/{publicId}/check-in
POST  /appointments/{publicId}/reschedule
POST  /prescriptions/{publicId}/issue
```

Expected status codes:

```text
200
201
204
400
401
403
404
409
```

Expected errors use stable domain codes and correlation IDs.

---

# 12. Swagger and Postman

AkosMed is backend-first, so API inspection/testing is incremental.

When endpoints begin to exist:

```text
endpoint implementation
→ OpenAPI/Swagger update
→ Postman request/scenario
→ automated tests
```

Swagger becomes the canonical live HTTP contract once controllers exist.

The official Postman collection grows with the project and is consolidated during final end-to-end validation.

---

# 13. Transactions

Service is the transaction boundary.

```text
read → @Transactional(readOnly = true)
write → @Transactional
```

Do not place transaction-sensitive business logic in controllers.

---

# 14. Concurrency

Three separate problems use separate mechanisms:

```text
PESSIMISTIC_WRITE
→ two requests competing for a scarce resource
→ appointment slot

@Version
→ concurrent updates to the same mutable row
→ lost update protection

Idempotency-Key
→ repeated request after retry/timeout/double-click
→ duplicate effect protection
```

## Appointment booking

Creation/rescheduling must:

```text
@Transactional
→ lock destination professional
→ revalidate availability
→ validate schedule blocks
→ check overlap
→ persist appointment
→ record AppointmentEvent
→ commit
```

Overlap rule:

```text
existing.startAt < newEnd
AND
existing.endAt > newStart
```

Interval semantics:

```text
[start, end)
```

Concurrent attempts for the same professional/period must end as:

```text
1 success
1 APPOINTMENT_CONFLICT
```

This is revalidated with real PostgreSQL transactions through Testcontainers before production readiness.

---

# 15. Time

Provide a central `Clock` bean.

Avoid scattering direct `now()` calls through services.

Use:

```text
LocalDate  → date without time
LocalTime  → recurring schedule time
Instant    → absolute persisted event time
OffsetDateTime → API contract when offset matters
```

Persist real instants in UTC.

Interpret/display local scheduling through `Tenant.timezone`.

Tests for time-dependent behavior use `Clock.fixed(...)`.

---

# 16. Clinical history

Clinical history is preserved.

Do not hard-delete or silently overwrite finalized:

- MedicalRecord;
- completed Encounter;
- ClinicalNote;
- issued Prescription;
- issued ClinicalDocument;
- finalized ExamResult;
- AppointmentEvent;
- AuditLog.

Corrections create explicit historical records or state transitions.

---

# 17. Storage

Large clinical files are not stored as PostgreSQL BLOBs by default.

The database stores metadata/references.

`StorageService` hides provider-specific behavior.

Development may use local filesystem. Production may use S3-compatible/object storage.

Authorization happens before file access.

---

# 18. Pagination and query safety

Paginate resources that can grow significantly, especially:

- patients;
- professionals;
- appointments;
- encounters;
- prescriptions;
- exam history;
- care plan history;
- notifications;
- audit logs.

Do not rely on accidental database ordering.

Whitelist externally accepted sort fields when necessary.

---

# 19. Logging and correlation

Every request accepts or generates:

```http
X-Correlation-Id
```

Use the same value in logs and API errors.

Never log:

- plaintext password;
- full JWT;
- refresh token;
- full clinical note;
- full prescription body;
- private file contents.

---

# 20. Testing policy

Each feature should test at least:

```text
happy path
validation
not found
conflict/state rule
publicId behavior
tenant isolation
unit access when applicable
```

Critical modules add:

```text
concurrency
Clock/time
optimistic locking
idempotency
clinical history immutability
```

A feature is not complete because a test file exists. Tests must actually run and pass.

---

# 21. Review severity

When using AI/review support, findings are grouped as:

```text
CRITICAL
IMPORTANT
IMPROVEMENT
```

Backend implementation remains manual unless explicitly requested otherwise. Review/support may provide reference snippets, explain design choices and inspect completed code.
